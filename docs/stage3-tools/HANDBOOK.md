# 链路 3：工具手册

版本：0.5（2026-11-09）

本手册写给负责链路 3（工具链）的会话。它说明工具链要做成什么、现在做到哪一步、按什么顺序推进、哪些事不归它管。

三条链路的关系、术语、来源等级见 [../OVERVIEW.md](../OVERVIEW.md)，**开工前先读**。本手册里凡是涉及链路 1、链路 2 的地方，以 OVERVIEW 为准。

**本手册专用的术语**：

- **工具链**：本工程里链路 3 的代码和规则。
- **项目**：使用工具链做具体地图的另一个目录，目录结构见 [../stage1-design/project-layout.md](../stage1-design/project-layout.md) 和本手册第 3 节。
- **负责人**：委托你开发工具链、审定本手册的人。手册里所有“要确认”的事都找负责人，不找项目。

---

## 1. 目的

做一套**通用**的《求生之路 2》（Left 4 Dead 2，下文简称 L4D2）地图制作工具链，让 AI 能够主导建图：

- 输入一份与具体项目无关的**场景描述**：多边形、高度、材质名、实体、实体连线。
- 输出三样东西：
  1. 能在 Hammer 里打开、查看、手工修改的地图源文件；
  2. 能在 L4D2 里加载游玩的地图；
  3. 能上传创意工坊的插件包。

**通用**的意思是：真实地点、雪山、极地、城市地标或虚构场景，工具链本身一行都不用改。工具链里不出现任何具体项目的地名、坐标、建筑或关卡内容。场景描述由链路 2 按链路 1 的搭建规格写出（OVERVIEW 第 1 节），写场景描述用的转换脚本放在项目里，不属于工具链。

**AI 主导**的意思是：AI 不操作 Hammer 的图形界面。AI 的工作方式是：

1. 写脚本生成地图；
2. 用脚本自动检查结果；
3. 不打开游戏，把地图渲染成预览图自查。

人负责 AI 做不了或做不好的事：在 Hammer 里手工微调、生成和修正导航网格、进游戏试玩、判断手感和节奏。

## 2. 边界

### 2.1 工具链负责

- 定义场景描述格式，并校验输入。
- 把场景描述转换成 Source 引擎格式：笔刷、实体、贴图（VTF/VMT）、模型（MDL）。
- 组织地图文件，保证生成内容和人工修改长期共存。
- 编译、检查、预览、打包、安装、上传。
- 常用玩法的实体模板，例如安全屋、尸潮事件、计时按钮、终局。

### 2.2 工具链不负责

| 事情 | 由谁负责 |
|---|---|
| 场景设计：建筑怎么布局、门开在哪、路线怎么走、玩法放哪里 | 链路 1（见 OVERVIEW 第 1 节的判别规则） |
| 美术内容：贴图画什么、模型长什么样 | 项目。项目交给工具链的是贴图图片和建模脚本（或 SMD 文件）；工具链负责运行建模脚本、编译和转换格式 |
| 把链路 1 的搭建规格转换成场景描述，并决定摆放、贴图和材质 | 链路 2 |
| 导航网格、试玩、平衡 | 人 |

遇到这些事时，工具链不替项目做决定：

- **格式错误或缺必填字段**：停止并报错。
- **引用的材质不存在**：自动换成开发占位材质（`dev/dev_measuregeneric01`），构建继续，在报告里列出被替换的材质。
- **引用的模型不存在**：停止并报错。模型影响碰撞，不能静默替换。

### 2.3 测试样例的原则

工具链的每项能力都只用**人造的最小样例**测试，比如一个 L 形房间、一扇门、一段楼梯、一块斜坡地形。不用任何真实地点或真实项目的数据。

每个样例本身就是一个最小的“项目”，放在 `samples/<样例名>/` 下，按第 3 节的项目结构组织（有自己的 `mapkit.json`、`scenes/`、`maps_src/`、`build/`）。工具链对样例和真实项目用同一套流程，这样样例跑通就等于流程跑通。

## 3. 目录约定

工具链根目录：本工程的根目录（下文 `<工具链>`）。

| 目录 | 内容 |
|---|---|
| `docs/` | 本手册和格式说明 |
| `mapkit/` | 工具链的 Python 代码 |
| `samples/` | 人造测试样例，每个是一个最小项目 |
| `vendor/` | 下载的第三方工具（Blender 等），不纳入版本管理 |
| `.venv/` | Python 虚拟环境，不纳入版本管理 |
| `mapkit.local.json` | 本机配置：游戏安装路径、Blender 路径等。不纳入版本管理 |

**调用方式**（`<py>` 指 `<工具链>\.venv\Scripts\python.exe`）：

| 命令 | 作用 |
|---|---|
| `<py> -m mapkit build <项目目录> <地图名>` | 构建一张地图：生成、编译、检查。产物在 `build/` |
| `<py> -m mapkit pack <项目目录>` | 把项目配置里列出的所有地图（取各自最近一次构建的 BSP 和 `maps_src` 里的 `.nav`）连同资源、`addoninfo.txt`、战役定义文件打成一个插件包 |
| `<py> -m mapkit sync <项目目录>` / `unsync` | 把自制资源同步到游戏目录 / 删掉同步过去的文件（规则 6） |

工具链只读 `scenes/<地图名>.json`，不调用项目里的任何脚本；场景描述由链路 2 先写好。

使用工具链的项目里，约定下面的结构。工具链按这个结构读写，项目名、地图名都由项目在配置里给出：

| 位置（相对项目根目录） | 内容 | 谁写 |
|---|---|---|
| `mapkit.json` | 项目配置，格式见 `docs/project-config.md`（第 7 节第 2 步定义） | 项目 |
| `scenes/<地图名>.json` | 场景描述 | 链路 2 |
| `assets/` | 美术源文件：贴图图片、建模脚本或 SMD、音效 WAV。具体结构随资源能力（第 7 节第 6 步）定义 | 项目 |
| `maps_src/<地图名>.vmf` | 主地图，人工编辑的源文件 | 工具链只在不存在时创建一次，之后归人 |
| `maps_src/<地图名>.nav` | 导航网格 | 人在游戏里生成后放这里 |
| `build/` | 构建产物，工具链写，可以整个删掉重建。子目录见下 | 工具链 |

`build/` 的子目录：

| 子目录 | 内容 |
|---|---|
| `build/instances/` | 生成的 instance 文件 |
| `build/game/` | 编译用的临时游戏目录：`gameinfo.txt`，以及转换好的自制材质、模型、音效 |
| `build/maps/` | 主地图的编译副本和编译结果（BSP、日志） |
| `build/reports/` | 检查报告和预览图 |
| `build/<插件名>/` | 打包目录。`vpk.exe` 会在旁边生成 `build/<插件名>.vpk`，即插件包 |

**编译方式**：

- 主地图里 `func_instance` 的路径写成 `../build/instances/gen_<地图名>.vmf`。在 Hammer 里打开 `maps_src/<地图名>.vmf` 时，按这个路径能找到生成内容。
- 每次构建把主地图复制到 `build/maps/`，复制时把路径改写成 `../instances/gen_<地图名>.vmf`，再编译这份副本。这样编译器的输出（BSP、日志等）都留在 `build/` 里，`maps_src/` 保持干净。
- vbsp 按主地图所在目录解析相对路径。2026-11-06 实测：主地图放在 `<项目>/maps_src/` 用 `../build/instances/...`、副本放在 `<项目>/build/maps/` 用 `../instances/...`，两种都能编译进 instance 的内容。
- 人在主地图里不要再加其他相对路径的 `func_instance`；需要复用的部件放进生成内容。复制时发现主地图里还有别的相对路径，构建报错。


### 3.1 项目仓库约定（2026-11-09）

参照 GitHub 上公开的 Source 地图仓库的通行做法（noodlecollie/l4d2maps、noodlecollie/tf2maps、ReactiveDrop/reactivedrop_public_src、HorseyHangout/au_skeld 等）：

| 内容 | 处理 | 理由 |
|---|---|---|
| `maps_src/*.vmf` 主地图、生成用的场景描述、设计文档、脚本 | 普通 git 提交 | 文本，压缩率高、能看差异。l4d2maps 435 个 VMF 共 900 MB，仓库只有 131 MB |
| `maps_src/*.nav` 导航网格 | 普通 git 提交 | 人工生成和修正，不能自动重来；单个通常几 MB |
| `assets/` 里的贴图源图、建模源文件、音效 | Git LFS | 二进制，每改一次都整份存；规模小时也可以直接提交 |
| `build/` 全部：编译出的 BSP、生成的 instance、转换好的 VTF 和 MDL、插件包 VPK | 不提交 | 都能从源文件重建。原版 BSP 中位数 24 MB，插件包几百 MB |
| 编译副产物 `*.prt *.lin *.vmx *.log` | 不提交 | 编译器临时文件 |
| 发布版插件 | 不进仓库，发创意工坊 | |

`.gitattributes` 里 VMF 标成 `*.vmf -merge -text`：参与 diff，但不自动合并、不转换换行。VMF 合并冲突只能人在 Hammer 里重新改，不要让 git 自动合出一个坏文件。

不要把 VMF 打成压缩包提交，压缩包每次都整份重存，也看不到差异。

现成的 `.gitignore` 和 `.gitattributes` 在 `templates/project/`。

## 4. 硬性规则

这些规则已经验证过或者是安全底线。要改先和负责人确认。

1. **工具链不含项目内容。** 代码、样例、文档里不出现任何具体项目的地名、坐标或数据。
   - 本仓库是公开的。提到“哪个项目在用”“从哪个项目来”也属于项目内容，同样不写；经验只写成不带出处的规则。
   - 提交前运行 `tools/check_clean.py`，它按 `tools/forbidden.local.txt`（每行一个关键词，不纳入版本管理）扫描所有纳入版本管理的文件，命中就不能提交。
2. **脚本只写生成文件，绝不写主地图。**
   - 主地图 `maps_src/<地图名>.vmf` 只在不存在时创建一次，之后永不写入、删除或移动。
   - 生成内容写进 `build/instances/` 下的 instance 文件，主地图用 `func_instance` 引用它。
   - 主地图首次创建时放：一个 `func_instance`（指向这张图的生成总文件），以及 `worldspawn` 的设置（天空名等，取自场景描述）。其余都在生成内容里：
     - **工具链自动生成的只有天空盒外壳**：按场景范围外扩 512 单位、厚 32 单位的封闭方盒，材质 `tools/toolsskybox`。
     - 地面、地形、光照、雾、出生点、安全屋、玩法实体，全部来自场景描述，工具链只负责转换，不自己决定放在哪。
   - **`worldspawn` 只在主地图里生效**：instance 里的 `worldspawn` 设置编译时会被忽略（已实测）。所以天空名这类设置只能在首次创建时写入；以后场景描述改了这些设置，工具链在报告里提醒人到 Hammer 里手改，不自动改主地图。
   - 生成内容需要拆成多个文件时，由生成的总文件再去引用，主地图里只引用一次。这样以后新增内容不用改主地图。
   - 主地图里的 `func_instance` 固定在原点 `0 0 0`、角度 `0 0 0`，不要移动。
   - `func_instance` 用 `fixup_style 0`（加前缀），主地图里的 `func_instance` 统一命名为 `gen`。2026-11-06 实测的前缀规则：
     - instance 里的实体名编译后变成 `gen-<原名>`，例如 `gen-orient_a`。主地图里的人工实体要连生成的实体，用带前缀的全名。
     - instance 里的输出指向的名字**也会被加前缀**，即使那个实体在主地图里。所以生成内容要连主地图或全局的实体，目标名必须以 `@` 开头（`@` 开头的名字不加前缀），例如 `@director`。
     - 第 7 步的连线检查在编译后的 BSP 上做，比对的是加完前缀的最终名字。
   - 生成的 instance 文件在 Hammer 里只看不改，下次构建会覆盖。要改就改输入。
3. **坐标约定。**
   - 场景描述用米，右手坐标：x 向东、y 向北、z 向上。
   - 换算成 Hammer 单位：1 单位 = 2.54 cm，即 1 米 ≈ 39.37 单位。不翻转任何轴。
   - 每张地图有一个原点（米，三维 x、y、z），由项目配置给出。场景描述里的坐标是项目自己的坐标，工具链先减去原点再换算。原点定下后不要改，否则主地图里人工放的东西会整体错位。
   - **范围**：场景内容换算后必须在 ±15000 单位以内；工具链自动加的天空盒外壳在此基础上向外留 512 单位，仍在 ±16384 以内。
   - **角度**：场景描述里的水平朝向用数学角度，从 +x（东）起逆时针为正，单位度，和 Source 的 yaw 一致。不用罗盘方位角。
   - **多边形**：顶点从上往下看按逆时针排列；顺时针的输入由工具链翻转，并在报告里提示。带洞多边形的洞按顺时针排列。
4. **防镜像。**
   - 场景描述里必须给出至少四个方位参照点（名字、米制坐标），四点不共面。工具链把它们生成为 `info_target`，名字是 `orient_<名字>`，编译后的全名是 `gen-orient_<名字>`。
   - 编译后从 BSP 读回这些点，用**独立实现的反向换算**（单位 → 米，加回原点）得到米制坐标，与场景描述比对，误差小于 0.1 m。反向换算不能复用正向换算的代码，否则正向写错了也查不出来。
   - 为什么要四点不共面：三维里，任何镜像都会让镜面上的点保持不动。三个点总在一个平面上，以这个平面为镜面的镜像查不出来；四个不共面的点才能查出所有镜像。
   - 几何本身的镜像（比如多边形顶点顺序或某个轴写反）由第 8 节的“几何一致”检查兜底。
5. **资源前缀。** 项目的所有自制资源都放在项目配置指定的前缀目录下，例如 `materials/<前缀>/`、`models/<前缀>/`、`sound/<前缀>/`，避免和原版或其他插件冲突。
6. **不动游戏原版文件。**
   - 往游戏目录同步（第 7 节第 6 步）时，目标是游戏的 `left4dead2\` 目录，只能写入、删除项目前缀下的目录：`materials/<前缀>/`、`materials/models/<前缀>/`、`models/<前缀>/`、`sound/<前缀>/`。同步只为了让 Hammer 显示自制资源；地图本身不同步，游戏里测试一律装插件包。
   - 编译用的临时 `gameinfo.txt` 也挂着游戏的 `left4dead2\` 目录，同步过去的散文件会让编译“找得到”资源，`build/game/` 里漏掉的东西就查不出来。所以 `build` 开始前，如果发现游戏目录里有同步的散文件，先自动执行 `unsync`，编译完成后再按需 `sync`。
   - 测试插件包之前，同样要先 `unsync`。否则游戏会优先读散文件，插件包里漏掉的东西也发现不了。
   - **安装插件包**：只能写入游戏的 `left4dead2\addons\<插件名>.vpk` 这一个文件，由人执行，或者在负责人明确要求时由 AI 执行。
7. **原版道具**：只有模型带 `static_prop` 标志、而且没有 `prop_data` 时才能用作 `prop_static`，否则改用 `prop_dynamic`。
8. **打包用游戏自带的 `vpk.exe`**，不用 srctools 写 VPK，它写单文件 VPK 有缺陷。
9. **只做验证所需的最小样例。** 不做会被丢弃的内容。
10. **测试不碰真实的主地图。** 需要模拟“人在 Hammer 里改主地图”的测试（比如验证人工修改能保留），先把样例整个复制到系统临时目录，在副本上修改和构建，测完删掉副本。工具链的正式代码里不允许出现写主地图的路径。

## 5. 场景描述（输入格式，待定义）

这是工具链最核心的接口，目前还没有定义。要求：

- 只表达几何和实体，不表达任何项目语义。比如说“这是一个房间，有四面墙和一个门洞”，而不说“这是卧室”。
- 人能读、AI 能写，用 JSON。
- 每个元素可以带 `source` 和 `note` 字段，让项目记录这条数据从哪来、为什么这样定，工具链只透传、不解读。
- 要覆盖的内容（初步）：
  - **实心体**：任意多边形（凸或凹、可带洞）加底高和顶高。
  - **空间**：房间、走廊等空心区域，墙厚和墙材质，地面、天花板材质。
  - **开口**：门洞、窗洞，所在墙面、位置、宽、高。
  - **楼板和楼层**：层高、楼板厚度。
  - **楼梯和坡道**：起点、终点、宽度、台阶高度。
  - **地形**：高度场或控制点，生成 displacement。
  - **材质**：每个面用哪种材质，以及材质在真实世界的尺寸（用来算贴图缩放）。
  - **实体**：类名、位置、角度、属性、连线。
  - **模型摆放**：模型路径、位置、角度、是否静态。
  - **玩法模板**：调用工具链提供的模板并传参数，例如“在这里放一个安全屋门”。
  - **地图设置**：天空名、光照、雾（会写进主地图的 `worldspawn` 和生成内容）。
  - **方位参照点**：至少四个不共面的点，见规则 4。
  - **出生点**：L4D2 战役第一张图用 `info_player_start`；中间关卡由安全屋决定，不单独放。
- 格式定义和说明写在 `docs/scene-format.md`，样例放在 `samples/`。
- 第一版只需覆盖第 7 节第 2 步列的内容；后面每加一项几何或资源能力，同步扩展格式，并升版本号。场景描述文件里要带格式版本号。

## 6. 能力清单与现状

状态说明：**已验证**表示做过最小样例并通过检查；**部分**表示做过但有已知问题；**未验证**表示还没做过。

| # | 能力 | 状态 | 说明 |
|---|---|---|---|

## 7. 工作顺序

按顺序推进。每完成一项，向负责人汇报：做了什么、怎么验证的、结果如何、有什么限制。不要一口气做完再汇报。

| 步骤 | 事项 | 完成标准 |
|---|---|---|
| 1 | 搭环境：建 `.venv`（srctools 2.7、shapely 2.1 或以上、numpy、pillow）；写 `mapkit.local.json`。第三方工具已在 `vendor/`（2026-11-09 实测：Blender 4.5.9 无界面启动、Source Tools 3.4.3 启用正常） | `.venv` 能导入四个包；按 `mapkit.local.json` 的路径能启动 Blender 并启用 Source Tools |
| 2 | 定义第一版格式：场景描述只含实心体（凸多边形拉伸）、材质、实体、地图设置、方位参照点；同时定义项目配置 `mapkit.json` | `docs/scene-format.md` 和 `docs/project-config.md`；一个人造样例；校验程序能指出格式错误（故意改坏样例能报出来） |
| 3 | `build` 和 `pack` 两条命令：读配置和场景描述 → 生成 instance（含天空盒外壳）→ 首次创建主地图 → 复制并编译 → 检查；`pack` 组装打包目录并打包。迁移旧代码时去掉项目内容，A1、B1 在新流程里重测 | 第 8 节所有检查通过；按规则 10 在副本上测试：改场景描述重建后主地图不变、人工加在主地图里的东西还在；`vpk.exe l` 能列出 `addoninfo.txt`、`missions/<插件名>.txt`、`maps/<地图名>.bsp` |
| 4 | 补齐几何能力 A2–A9 | 每项各有一个人造样例，编译通过，几何与输入一致（轮廓偏差小于 2 单位，面积差小于 0.1%） |
| 5 | 不开游戏的预览 D3：先提出方案交负责人确认，再实现 | 能输出俯视图和指定机位的透视图；把预览图交负责人看，确认看得出墙、门洞、楼层 |
| 6 | 资源：贴图 C1、C1b，模型 C2，音效 C3，同步 D5；扩展格式和 `assets/` 结构 | 编译日志无缺失资源；同步后由负责人在 Hammer 里确认显示正确 |
| 7 | 玩法模板 B4 | 每个模板一个样例，编译通过；连线检查：每个模板约定的输出都连到了存在的实体 |
| 8 | 插件和发布：D4、D6、C3 | 由负责人在游戏里确认：插件出现在战役列表并能加载、音效能循环播放；负责人走一遍上传 |

第 3 步的 `addoninfo.txt` 和战役定义文件先用最简内容（标题、作者、地图列表），字段由 `mapkit.json` 提供；第 8 步再按游戏里的实际表现补全。

第 4 步的“几何一致”标准对每种能力含义不同，分别是：

- 实心体、空间：俯视轮廓偏差小于 2 单位，面积差小于 0.1%。
- 开口：位置和宽高偏差小于 1 单位。
- 楼板：高度偏差小于 1 单位。
- 楼梯：每级台阶高度不超过 18 单位（L4D2 玩家能直接走上的高度），总高偏差小于 1 单位。
- 地形：采样点高度偏差小于 4 单位。

需要负责人在 Hammer 或游戏里确认的步骤（5、6、8），提前约时间。

## 8. 自动检查

| 检查 | 标准 | 不通过时 |
|---|---|---|
| 输入格式 | 符合场景描述格式 | 停止，指出哪一条数据有问题 |
| 坐标范围 | 全部在 ±15000 单位以内 | 停止，提示调整原点或缩小场景 |
| 防镜像 | 参照点误差小于 0.1 m（规则 4） | 停止 |
| 漏点 | vbsp 没有报 leak | 停止，附日志和漏点位置 |
| 编译报错 | 没有 error | 停止，附日志 |
| 缺资源 | 构建前检查：场景描述引用的每个材质和模型，都能在原版 VPK 或 `build/game/` 里找到。编译后再查日志有没有缺失报告 | 材质：换占位并警告；模型：停止 |
| 数量预算 | 编译后的地图：实体不超过 1200，笔刷不超过 6000，平面不超过 50000 | 警告并报告数量 |
| 几何一致 | 按第 7 节第 4 步的标准。轮廓比对用**对称差面积比**（两者不重合部分的面积 ÷ 输入面积）和 Hausdorff 距离，不用单纯的面积差，否则镜像后面积一样也查不出来。从 BSP 读回的坐标用规则 4 的独立反向换算。只比对生成内容：读回时只取场景描述里声明的范围和高度上的面，主地图里人工加的东西不参与 | 停止 |

**日志判定口径**：

- 编译工具的退出码不为 0，就算失败。
- 漏点：vbsp 日志里出现 `LEAKED`，或者生成了 `<地图名>.lin` 文件。漏点路径从 `.lin` 文件读出，写进报告。
- 报错：日志里以 `Error` 开头的行。
- 缺资源：vbsp 和 vrad 日志里含 `not found`、`missing` 的行，以及加载模型失败的行。

数量预算不是引擎上限，是参照原版地图定的安全线。原版全部 59 张战役地图（编译后的 BSP，2026-11-09 重新统计）：实体中位数 1139（最多 2351，c6m1_riverbank），笔刷中位数 2747（最多 6369，c10m4_mainstreet），平面中位数 14816（最多 59990，c2m3_coaster）。

编译后 BSP 里的实体数不等于运行时实体数：编译时很多实体会被合并或去掉，运行时又会加上刷出的感染者、掉落物等。原版最多的一张有 2351 个，超过运行时上限 2048 也能运行，所以 BSP 实体数只作参考，不和 2048 直接比较。

`mapkit.local.json`（本机配置）的字段：

| 字段 | 含义 |
|---|---|
| `game_dir` | L4D2 安装目录 |
| `blender` | `blender.exe` 的路径 |
| `blender_scripts` | Source Tools 的上级目录，即 `BLENDER_USER_SCRIPTS` 的值 |

使用要点：

- 编译工具（vbsp、vvis、vrad、studiomdl）都用 `-game build/game` 指向临时游戏目录。该目录里的 `gameinfo.txt` 第一个搜索路径是它自己（放自制资源），后面按顺序挂进原版游戏的各个内容目录。这样不用往游戏目录写东西也能编译。模板（`<游戏目录>` 换成 `mapkit.local.json` 的 `game_dir`）：

  ```text
  "GameInfo"
  {
  	game	"MapKit build stage"
  	type multiplayer_only
  	nomodels 1
  	nohimodel 1
  	GameData	"left4dead2.fgd"
  	FileSystem
  	{
  		SteamAppId	550
  		ToolsAppId	563
  		SearchPaths
  		{
  			Game	|gameinfo_path|.
  			Game	"<游戏目录>\update"
  			Game	"<游戏目录>\left4dead2_dlc3"
  			Game	"<游戏目录>\left4dead2_dlc2"
  			Game	"<游戏目录>\left4dead2_dlc1"
  			Game	"<游戏目录>\left4dead2"
  			Game	"<游戏目录>\hl2"
  		}
  	}
  }
  ```

- 写贴图：用 PIL 把图片转成 RGBA，宽高必须是 2 的幂；`srctools.vtf.VTF(宽, 高, version=(7, 4), fmt=ImageFormats.DXT1)`（带透明用 DXT5，并加 `VTFFlags.EIGHTBITALPHA`），`vtf.get().copy_from(img.tobytes())`，`vtf.compute_mipmaps()`，再 `vtf.save(文件)`。VMT 是纯文本：笔刷用 `LightmappedGeneric`，模型用 `VertexLitGeneric`，至少写 `$basetexture` 和 `$surfaceprop`。
- 凹多边形拆凸块：先三角化，再把相邻三角形贪心合并，合并后仍是凸多边形就保留。三角化必须用约束三角化（shapely 2.1 的 `constrained_delaunay_triangles`），普通 Delaunay 在凹形上会出错（见能力 A2）。
- 任意朝向的棱柱笔刷：每个侧面用底边两点加一个顶边点定义平面，三点按从外面看顺时针排列；顶面、底面各取三个顶点。侧面的贴图 U 轴取底边方向，V 轴取竖直向下。
- Blender 用无界面模式运行（`--background --factory-startup`），设置环境变量 `BLENDER_USER_SCRIPTS`，脚本里调用 `addon_utils.enable("io_scene_valvesource")` 启用插件。
- 模型编译：`studiomdl.exe -nop4 -game <目录> <qc 文件>`。
- 打包：`vpk.exe <目录>`，会在该目录旁边生成同名的单文件 VPK。
- 读 VMF：`VMF.parse(Keyvalues.parse(f))`。

### 标尺

**1 单位 = 1 英寸 = 2.54 cm，即 1 米 ≈ 39.37 单位。** 工具链的坐标换算（规则 3）按这个比例。

依据：

| 证据 | 内容 |
|---|---|
| 引擎写死的人物尺寸 | 站立碰撞体高 72 单位（SDK `game/shared/gamerules.cpp` 的 `VEC_HULL_MAX`），按 1 英寸换算 1.83 m，是正常身高 |
| Valve 源码注释 | 跌落伤害等处按 1 英尺 = 12 单位写，例如 `approx 60 feet sqrt(2 * gravity * 60 * 12)` |
| 社区工具 | Blender 导入插件 Plumber 的说明：0.0254 可以得到更真实的比例 |

**注意：原版的门、车、家具比真实尺寸大 20%–60%。** 按 1 英寸换算，原版门 `doormain01` 宽 56、高 104 单位，即 1.42 × 2.64 m；轿车 `cara_95sedan` 223 单位长，即 5.66 m。Valve 的做法是“人按真实比例，环境放大一号”，方便 4 个人和 AI 走动。网上流传的“1 单位 = 1.905 cm”就是从这里来的：按它算门和车刚好是真实尺寸，但人只有 1.37 m。所以：

- 换算比例统一用 2.54 cm；
- 门、走廊、楼梯的宽度按原版习惯放大，具体数值由链路 1、2 定，工具链不自动放大。

其他常用数字（SDK 和原版数据实测）：

| 项目 | 数值 |
|---|---|
| 幸存者站立碰撞体 | 宽 32、高 72 单位；视线高 64 |
| 蹲下碰撞体 | 高 36 单位 |
| 跳跃高度 | 21 单位 |
| 能直接走上的台阶 | 18 单位 |
| 幸存者跑速 | 220 单位/秒，约 5.6 m/s |
| 一张图的可用边长 | 32768 单位约 832 m；扣掉天空盒和边界，规划按约 730 m 预算 |

### 读原版资源

链路 1 核实玩法、链路 2 找材质和模型、工具链做检查，都要读原版游戏文件。都用项目或工具链 `.venv` 里的 srctools，只读，不改游戏文件。

| 读什么 | 在哪 | 怎么读 |
|---|---|---|
| 原版地图 | 游戏目录下各内容目录的 `maps\*.bsp`（`left4dead2`、`left4dead2_dlc1` 到 `dlc3`、`update`），不在 VPK 里。战役图共 59 张 | `srctools.bsp.BSP(path)`；`.ents.entities` 是实体列表，每个实体可按键取值，`.outputs` 是连线；`.planes`、`.brushes`、`.vertexes`、`.faces` 是几何 |
| 模型和材质 | 各内容目录的 `pak01_dir.vpk`。查找顺序和游戏一致：`update`、`left4dead2_dlc3`、`left4dead2_dlc2`、`left4dead2_dlc1`、`left4dead2` | `srctools.filesys.VPKFileSystem(path)` 打开；模型用 `srctools.mdl.Model(fs, fs[路径])`，有 `hull_min`、`hull_max`、`flags`、`keyvalues`；材质的 VMT 用 `fs[路径].open_str()` 读文本，贴图用 `srctools.vtf.VTF.read(...)` |
| 音效 | `left4dead2\sound\` 下的散文件 | 直接按文件读 |
| 实体类和输入输出的定义 | 游戏 `bin\left4dead2.fgd`、`bin\base.fgd` | 文本文件，按类名查 |

常见做法：

- **找玩法先例**：遍历原版地图的实体，按类名（如 `func_button_timed`、`trigger_finale`、`prop_car_alarm`）筛出来，看它的属性和 `.outputs` 连到哪里。
- **量尺寸**：模型的 `hull_max - hull_min`；笔刷实体用 BSP 里对应 bmodel 的 `maxes - mins`。
- **原版的终局和尸潮脚本**在 VPK 的 `scripts/vscripts/` 下，很多是加密的 `.nuc`，读不了，只能从地图实体的连线反推。

### 13.3 验证 A：任意角度的真实轮廓变成笔刷（通过）

- 样本：一栋真实建筑的 OSM 轮廓，L 形，两翼都不是正南正北，6 层，按 1 单位 = 2.54 cm 换算。
- 做法：轮廓三角化后合并成凸块（拆成 2 块），每块拉伸成一个任意朝向的棱柱笔刷。
- 结果：
  - vbsp、vvis、vrad 无报错、无漏点。
  - 方法：从编译后的 BSP 里取出所有在楼顶高度、法线朝上的面，合并成一个多边形，和输入轮廓比对。
  - 与 OSM 轮廓的最大偏差 0.005 单位，面积差 0.0002%。
  - L 形内拐角在 BSP 里的位置与输入一致，没有镜像。
- 注意：地理坐标的原点通常离场景几百米，直接换算会超出 ±16384 的地图范围，所以每张地图要有自己的原点（规则 3）。

### 13.4 验证 B：生成内容和手工编辑共存（通过）

- 做法：生成的内容写进 instance 文件；主地图只在第一次创建，之后归手工编辑，用 `func_instance` 引用生成文件。当时主地图和 instance 放在同一目录，与第 3 节的布局不同；第 3 节的布局另行实测过（见第 3 节“编译方式”）。
- 过程：生成 6 层的楼 → 模拟在 Hammer 里给主地图加一个箱子和一盏灯 → 改输入为 7 层并只重新生成 instance → 编译主地图。
- 结果：第二次编译后楼高从 780 变成 909 单位，手加的箱子和灯都在，instance 里的实体也带进了 BSP。
- 结论：以后的规则是“脚本只写 instance 文件，绝不写主地图”。

### 13.5 已知问题与约定

1. **自制资源要同步到游戏目录**：Hammer 只从游戏目录读资源，要在构建后自动复制。
2. **原版模型分静态和动态**：很多原版道具不能当 `prop_static` 用，生成时要先查模型标志（`Flags.static_prop` 且没有 `prop_data`）。
3. **srctools 写单文件 VPK 有缺陷**：打包用游戏自带的 `vpk.exe`。
4. **读 VMF**：用 `VMF.parse(Keyvalues.parse(f))`。
