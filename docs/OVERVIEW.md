# 总览：链路、术语、来源与状态

版本：1.0（2026-11-09）

本文是所有手册共用的约定。三条链路的手册都以本文为准；手册之间有冲突时，以本文为准。

---

## 1. 三条链路的关系

| | 链路 1 设计 | 链路 2 搭建 | 链路 3 工具 |
|---|---|---|---|
| 性质 | 工作 | 工作 | 能力 |
| 输入 | 一个主题和负责人的意图 | 链路 1 的搭建规格 | 链路 2 写的场景描述 |
| 输出 | 设计材料 + 搭建规格 | 能玩的地图 | 地图文件、编译结果、插件包 |
| 对每张地图 | 走一遍 | 走一遍 | 不变，只按需补能力 |

- **方法上互相独立**：三条链路可以分开探索、分开验证。
- **生产上串行**：同一张地图先过链路 1，再过链路 2；链路 2 调用链路 3 的工具。不同地图之间可以错开流水，比如第一关在搭建时，第二关在设计。
- **链路 3 走在前面**：链路 2 需要什么能力，链路 3 就补什么能力。
- **白模是两条链路的交界**：链路 2 先做白模（只有墙、地、门、楼梯，没有贴图），它同时是链路 1 的验收。白模进游戏发现尺度、路线或节奏不对，退回链路 1 改设计。

**判别规则**（遇到“这件事归谁”时用）：

- 会改变玩家路线或选择的空间决定，归链路 1：门开在哪、走廊怎么连、开放哪几层、楼间距压缩到多少、哪里封路。
- 不影响玩法的外观决定，归链路 2：房间里摆什么、装饰性的房间、立面细节、贴图和材质。
- 怎样把这些决定变成 Source 引擎能用的东西，归链路 3：笔刷、实体、编译、打包。

## 2. 规范的作用

规范不是说顺序永远不能改。规范保证的是：AI 按规范先完整交付一版，这一版**达到可以评审的程度**。负责人看过以后，可能对任何一步提修改，改完从那一步往下重新推进。

每个交付物的“可评审底线”：

1. 没有空着不写的地方；暂时定不了的，写明是假设，并附一个问题给负责人。
2. 每个元素都标来源（第 4 节）和状态（第 5 节）。
3. 能自动校验的都校验了，校验报告随交付物一起给出。

## 3. 术语

### 3.1 结构

| 术语 | 含义 |
|---|---|
| 项目 | 一个地图作品，对应一个目录。如一部战役 |
| 战役 | 若干关卡连起来的一整部作品 |
| 关卡 | 一张地图（一个 BSP），从一个安全屋走到下一个安全屋 |
| 段落 | 关卡内按节奏划分的一段，编号 A、B、C… |
| 场景 | 一个具体地点，放 1–2 个玩法。一个段落可以有一个或几个场景 |
| 对象 | 现实或设定中的一个稳定实体：一个地点、一栋楼、楼的一个部位。资料按对象归档 |

### 3.2 内容

| 术语 | 含义 |
|---|---|
| 玩法 | 玩家能因此做出不同选择、或用不同方式通过的设计。判断标准：只能看、只能听的不算 |
| 背景 | 解释“为什么往这走”的设定，不是玩法 |
| 事件 | 导演触发的尸潮、Tank、Witch 等 |
| 守点 | 要在一个地方守一段时间的事件 |
| 安全屋 | 关卡起点和终点的房间 |
| 衔接点 | 相邻两关共用的安全屋；上一关的“进门”和下一关的“出门”坐标完全一致 |
| 封路 | 挡住某条路的设置。要定五件事：用什么挡、玩家能不能翻、感染者能不能翻、能不能看穿、为什么在这 |
| 可玩边界 | 玩家能到达的范围的外沿 |
| 远景 | 可玩边界以外看得见的景物，放在 3D 天空盒里 |
| 压缩 | 缩短楼与楼之间的空地，建筑本身不缩 |

### 3.3 资料

| 术语 | 含义 |
|---|---|
| 资料 | 原始证据：网页摘录、照片、全景截图、视频抽帧、地理数据、游戏文件实测、负责人口述。只增不改，每条有固定编号 |
| 结论 | 从资料得出的事实，必须引用资料编号 |
| 标准 | 项目级规则，例如标尺、坐标系 |
| 勘误 | 发现资料认错了，在索引里追加说明，不删原件 |

### 3.4 阶段和交付物

| 阶段 | 回答什么 | 最终材料 |
|---|---|---|
| 规划 | 做哪几关，每关走哪、玩什么、节奏怎样 | 战役概要、关卡设计、规划数据、规划图、校验报告 |
| 详设 | 每关的空间具体长什么样 | 空间总图、建筑分级表、室内平面图、剖面图、封路与边界清单、搭建规格、校验报告、待确认问题清单 |

**搭建规格**：链路 1 交给链路 2 的机器可读文件，是详设材料的合集。链路 2 拿到它就能搭，不需要再替设计做决定。

**场景描述**：链路 2 交给链路 3 的机器可读文件，只有几何和实体，没有设计语义。格式由链路 3 定义。

详细定义见 [stage1-design/deliverables.md](stage1-design/deliverables.md)。

## 4. 来源等级

资料、结论和设计元素都用同一套来源等级：

| 等级 | 含义 | 例子 |
|---|---|---|
| 实测 | 从数据直接量出来 | OSM 轮廓量出的楼长、游戏文件里读出的跑速 |
| 官方 | 官方发布的资料 | 学校官网、官方全景、官方地图 |
| 网络 | 网络公开资料，对象可以确认 | 新闻配图，能认出是哪栋楼 |
| 存疑 | 网络资料，对象不能确认 | 照片说是某楼，但看不出来 |
| 无关 | 和对象无关，只作风格参考 | 其他学校的同类建筑 |
| 确认 | 负责人或去过的人口述确认，带日期 | “东侧入口有三级台阶”（2026-01-15 确认） |
| 推断 | 从其他事实按规则推出来 | 楼宽够放两排房间，推断为中廊式 |
| 假设 | 没有依据，暂时这样定 | 楼梯间在端头 |
| 改动 | 明知和现实不同，为玩法改的 | 把一条路封死 |

写法：`来源：确认（2026-01-15）`、`来源：实测（OSM way/123456789）`、`来源：推断（S0123、S0124）`。

## 5. 状态

| 状态 | 含义 |
|---|---|
| 定稿 | 负责人认可，可以往下游交付 |
| 讨论中 | 有方案，负责人还在考虑 |
| 假设 | 先这样定，等资料或负责人确认 |
| 作废 | 不再采用；保留记录，写明原因和日期 |

## 6. 写给会话和模型的约定

- 新会话接手一个项目时，按顺序读：项目 `README.md` → 本文 → 当前链路的手册 → 项目里该阶段的材料。
- 结论要写进文件。对话里说过的结论，没写进文件就等于没有，其他会话看不到。
- 负责人口述的确认，当场记进资料库（`sources/oral/`），写上日期。
- 发现自己之前的结论错了，明确更正，写明错在哪；不悄悄改掉。
- 用简洁的中文，少用嵌套列表。数据要实测并注明来源。
