三条组织原则（其余规则都从这里推出来）

  1. 会话只是干活的载体，权限来自文件归属和拍板。每个文件只有一条线负责（见“依赖与归属”）。设计文件改了，拍板记录的指纹会让它变成“拍板后已修改”，谁改都绕不过负责人。
  2. 会话之间不发消息，只靠文件交接。交接写进本线日志和问题清单，下一个会话开工读文件。会话结束、上下文压缩都不丢东西。
  3. 会话只在段表列出的接力点换。负责人本来就要在接力点出现，在这里换会话不增加他的操作。段内的其他停顿点（D1 有压缩候选时、D4 彩蛋）照常停下讨论，不换会话。

排期规则

  1. 总控做完规划（P0–P4）和 D0 后转入待命，不再做步骤里的活。
  2. 同时开发最多 max_parallel_lines 关（模拟取 2）。一关从设计① 开工到 G9 交付占一个名额；G9 拍板后这一关让出名额，开下一关的设计①。
  3. 修订会话和等负责人试走的生成③ 不占名额。修订会话同一关同时只有一个，负责人同意后马上开。
  4. 每段结束都是接力点。负责人一次审一个，后到的排队（黄色）。审完由这一段的会话开下一段，自己结束。
  5. 一关设计做完 D7，由设计③ 直接开这一关的生成①，不排队。几条生成线同时改共用文件时：改前看 git status，改完按路径提交，别的关靠 stamps 发现。
  6. 生成① 在 G4 之后停一次，只交这一批要设计修订的问题；负责人同意后开修订会话（模拟里每关 1 次），生成② 照常往下做。

结束的会话写（交接）

  1. 本线日志 logs/L<nn>-design.md 或 -build.md 追加一节：这段做完了什么；负责人这次的决定（原话写进 design/REVIEW-LOG.md，日志只写日期）；留下的“假设”和它们影响哪些产物；本段新登记的问题编号；下一段从哪一步开始。
  2. PROJECT.md 主线分工表只改本线那一行：现在第几段、哪个会话、状态。不往 PROJECT.md 追加长段落。
  3. 只 add 自己改的文件并提交，再开下一段的会话（P0 授权了 auto_handoff 才自己开，没授权就把开场白交负责人）。开场白三句：用这个 skill；项目目录；“你负责 L<nn> 设计②”。然后结束。

新开的会话读（只读这些）

  1. Kit 的 SKILL.md、PROJECT.md、kit status。
  2. 本线日志的最后一节。
  3. 交给本线、还没关闭的问题，以及当前步骤的步骤页。
  4. 不读别的会话的对话记录，不读其他步骤页。读完能接着干，就说明交接写够了。

提前换：一段没做完但上下文已经压缩过一次，做完手上这一步就写交接、提前接力，不等接力点。压缩后的会话会忘细节，容易漏读别的线留下的交接。

#负责人总控设计侧会话（设计线 / 修订）生成线会话子 agent文件与脚本

问题清单的条目状态

只有接收方能把条目改成“已修复”或“已驳回”；只有发现方重跑完才能改成“已关闭”。“发现方”指一条线：由它当时在跑的会话关闭，整条线都结束了由总控关闭。一条只有一个结局，修复和驳回二选一。

循环什么时候停

  1. 每转一圈，要么关掉一条，要么登记一条新的再转；问题清单里没有“待处理”，kit status 也没有过期项，循环结束。
  2. 防乒乓：同一个设计元素（elements.json 的 key，没有 key 的按条目 id）第 3 次重开时，重开它的会话停下交负责人查根子。
  3. 挡路的才停：不挡后面全部工作的，带着“假设”继续做，并在条目里写清假设影响哪些产物；改完只重做这些。影响 G3 几何或导航的假设当挡路问题；只影响 G4–G7 的照做并登记。
  4. 成批交：交回设计的问题攒到本段的停顿点一起交，不一个一个打断负责人。
  5. 只改局部：机器部分（生成、核验、快速编译）整体重跑；AI 和人的产物只改受影响的那几处；拍板只交改动的那几条，负责人已答复过的取舍不再拍板。

P0 要你授权的一件事

会话按流程在接力点开下一段会话，要负责人在 P0 一次授权，写进 kit.local.json 的 agents.auto_handoff。环境能不能开会话另记在 new_session，两者分开。

  • 授权：你在接力点回复“可以”，下一段会话就出现在侧栏，你接着在新会话里对话。每段结束的消息里写明开了哪个会话、结束了哪个会话。
  • 不授权：每段结束时，会话把三句开场白写好，你自己开。会话数量不变，每关多 6–7 次手动操作。

其余都已按上面的原则定下：线会话之间不发消息；总控不做步骤里的活；每关自己走完设计和生成；修订由发现问题的会话在停顿点开；Kit 的问题只告诉你，改不改由你在流程外决定。
