# 评审、拍板与修改

用户不是关卡设计师。只在两种情况下停下来请用户拍板：只有他能定的事（方向、玩法取舍、他知道的现场事实、喜好），或者有依据可看、有建议可选的事。凭空让用户填数字、定参数，都不该出现。每一步要不要拍、拿什么拍，以那一步的步骤页为准。

少停、成批交：用户在意的是被频繁打断，不是要看的内容多。同一类内容攒成一批交，一栋楼、一段路做完就停是不对的。停在哪里以步骤页为准。

停下来是讨论：用户可以分几轮提意见，你改完再交，直到他说可以。每轮意见都记进 `REVIEW-LOG.md`，用户说可以了再一次登记。

## 交用户拍板的消息

**要用户拍板的问题一律放在消息最前面，明确提问。** 其他内容都放在后面。

按这个顺序写，用中文，少用技术词：

1. **要你定的**：逐条编号，每条是一个明确的问题，附你的判断或建议，用户能直接答“对 / 不对”或“选哪个”。有几种合理做法时列出选项和利弊，再说你推荐哪个。
2. **评审页**：步骤页要求附网页的，给链接；没有网页就不交。只需文字的步骤（如 P0 的安装许可、D2 的结构事实）把要确认的事直接写在第 1 项里，不要让用户去打开给 agent 用的文件（底稿、JSON）。
3. **只是告诉你的**：默认值、按规则推出来的东西、已经改掉的错误，一两句带过。用户觉得不对可以提。
4. **没过的核验**：哪项、为什么、打算怎么处理。全部通过就写一句“核验全部通过”。

已经拍过板的内容不要再混进“要你定的”里。指纹、字段名、内部编号尽量不出现。

**不问的东西**：规划里已经写定的设计（照做）；不在规划路线上的细节（按资料定，标“推断”）。每个问题发出前，先查规划原文有没有写过、这件事在不在路线上。

**拿不准该不该问时，不问**：按你的判断做，标出来（“推断”或“假设”），在“只是告诉你的”里一句带过。错了用户会在后面的评审页上看到，改起来比现在多问一句便宜。

分寸：停不停、问不问，按上面的规则办，不自由发挥；设计本身（玩法、节奏、要不要压缩）由你判断，附建议交用户定。

## 拍板

1. 用户说可以后，跑 `kit approve <单元> [<单元> …]`（单元名见 `kit status`），它会记下文件指纹。整关详设用 `kit approve L<nn>/detail`，一次登记这一关全部结构体和开放区。
2. 把用户意见写进 `design/REVIEW-LOG.md`，每条标“AI 本可避免”或“只有用户知道”。“AI 本可避免”的越多，说明前面的步骤越需要改进。
3. 提交（只提交自己改的文件），更新 `PROJECT.md`。

## 修改和过期

- 只改所属的那个文件。改了一个结构体，不需要动别的结构体。
- 改完跑 `kit status`，它会按依赖关系列出：
  - **过期**：生成物比源文件旧（核验报告、`levels.json`、规划视图、`spec.json`），或者核验报告用到的待决定列表数值改了（报告里记着它读过哪些项；没有这项记录的旧报告只按时间判断）。先由机器重跑：`kit detail structure`、`kit plan build`、`kit spec` 等。
  - **核验未过**：重跑后没通过的，回到对应步骤去改。
  - **拍板后已修改**：内容变了的单元，重新交用户拍板。只改数据错误、没改设计的，可以在下一次拍板（如整关拍板）时一并带过，一次登记多个单元。
- 不要求“后面全部重做”。一个改动影响多大，由过期列表决定。
