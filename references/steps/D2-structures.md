# D2 内部结构设计（结构事实清单讨论一次；画完和 D3 一起交）

**目的**：把每个可进入的结构体写成生成能直接照着搭的数据：先外壳，再竖向通道，最后只写需要的内部。

动手前读 [rules.md](../rules.md)。格式见 [format/structure.md](../format/structure.md)。
遇到门洞净宽、安全屋门、电梯、收集物等 L4D2 实体机制时，先按需渐进查询知识库：`kit kb list --step D2` 或 `kit kb search <词/类名>`，命中后再 `kit kb show <id>`；库里未覆盖的原版机制用 `kit game` 查实。

## 做

1. **先查清这一关所有可进入结构体的结构事实**：竖向通道有几处、在什么位置，公共区在哪，出入口朝哪，有没有挑空，哪些层要进。先跑 `kit sources find <对象> --use structure`；按结构体派轻量子 agent 并行调研。不在规划路线上的（外观、层数、屋顶设备，路线不进的房间）按资料定，照片优先，标“推断”，不问；在路线上的位置、尺寸、编号可以按游戏性调整，标“改动”，不问。

   **动手画之前，确认结构事实**。这是 D2 的第一个停顿点，可以讨论几轮。熟悉这个地方的用户常常知道资料里没有的事；画完再纠正要返工。分两样东西：

   - **底稿** `design/detail/L<nn>/FACTS.md`：给 agent 用，用户不用看。每个可进入的结构体（含本关要写的扩展）一节，每条标“查到”（附资料编号）或“推断”（附依据）。画结构体时照它写 `src`。
   - **给用户的消息**：能单独读懂，不需要打开任何文件。只写要用户确认的事，按对路线影响的大小排序，编号。每条写成“我判断是……（依据一句话）。对吗？”，让用户能回“3 不对，是两层”这样答。查到且没有疑问的事实不列；D1 的结论最多一句带过。

   **发之前逐条筛一遍**，只留第 3 类。判断“在不在路线上”只看规划：路线穿过的空间、要开的门、要走的楼梯、玩法物件所在的位置算在路线上，其余都不算：
   1. 规划里已经写定的（规划源文件的路线、分支、段落、安全屋，DESIGN.md 的段落叙述）：那是用户拍过板的设计，照做，不问。
   2. 不在路线上的（外观、层数、屋顶、路线不进的房间在哪一侧）：按等级最高的资料定，照片优先，标“推断”，不问。资料互相矛盾也一样。
   3. 在路线上、而且资料缺失或互相矛盾的（比如路线要穿过的两栋楼之间到底通不通、路线要上的楼梯在哪）：问。

   设计取舍（要不要做成地标、要不要多开一层）不是事实，放进“要你定的”，附建议，不混在事实里。

   拿不准该不该问时，不问：按你的判断做，标“推断”或“假设”。错了用户会在整关页上看到，改起来比现在多问一句便宜。

   用户答完：每条回答记进 `sources/oral/`（按口述入库，等级“确认”），按回答改底稿，在底稿开头写 `确认：<日期>`，然后开始画，中途不停。
2. **外壳**：从外面看得到的部分和出入口。台阶要接上门外的地面。
   - 规则建筑（平面轮廓加楼层）：用“轮廓按层拉伸 + 立面规则”表示，格式已经支持。只有外壳的结构体可以用 `kit detail scaffold facade` 起稿。
   - 不规则结构体（山洞、溶洞、异形建筑等）：现有格式表达不了。停下来，向用户说明需要表达什么、你建议怎么表示，由用户决定。
3. **竖向通道**：楼梯、坡道、梯子、竖井。约定全部写清；往上要封堵的，写明要建几级。
4. **内部**：只写会走进去或看得到的空间。进不去的房间只是墙上一扇关着的门。跨层的空间写成挑空。
5. **物件**：按三档随结构体一起写（[format/structure.md](../format/structure.md)）。翻越、视线写成字段，触发接到事件表。
6. **室内意图**：每个建出来的空间写一条 `interiors`（[format/structure.md](../format/structure.md) 的“室内意图”），没有互动物的空间也写：这是什么房间、出事后成了什么样；本来就该空的写为什么空；有特殊要求（照片要还原的、玩法要求的位置）才写 `must`。摆什么、怎么摆不写。
7. 大的结构体可以拆成一个外壳文件加每层一个文件（`parts`），改一层只需读那一层。
8. **共享结构体**：本关是写入关，写外壳和本关用到的部分，后一关会接着往里加，外壳要写全。本关不是写入关：只走写入关已经建好的部分时，只引用，不写文件；要走得更深时（`kit status` 会列为“扩展”），在本关写扩展文件（[format/structure.md](../format/structure.md) 的“扩展文件”），不改写入关的文件。扩展的结构事实也放进结构事实清单。

## 命令

`kit detail structure <文件>`：核验并生成 `.build.json`（交给生成）、`.check.json` 和 `.html`（评审页）。

## 子 agent

**轻量档**做两件事：
- 只有外壳的结构体，按脚手架批量起稿，起完必须过 `kit detail structure`。
- 动手画之前，按结构体并行调研结构事实，每个只交事实清单和资料编号，不做布局判断；主 agent 核对来源后汇总成清单。

## 拍板

整关只停两次，中途不停：

1. **结构事实确认**（上面第 1 项，文字）。`kit status` 看 `FACTS.md`：没有就提示先交；有了但开头没有 `确认：`，就提示等用户回答；确认了才提示开始画。
2. **整关详设**：这一关所有结构体和开放区（D3）都画完、核验全过后，跑 `kit page <n>`，用整关页一起交。消息按 [review.md](../review.md)，按结构体分节：
   - 要你定的：路线怎么走、进哪些房间、封堵在哪、玩法物件放在哪，每条附建议；画的过程中记下的 `questions` 在这里一起问；
   - 只是告诉你的：尺寸（由尺度目标和脚本兜底）、外壳细节、只有外壳的结构体。

例外：遇到这个项目第一次出现的结构类型（比如第一次做山洞），可以只在那一个结构体画完时先停一下看一眼。不规则结构体格式表达不了时，按上面第 2 项停下。

## 完成

`kit detail structure` 全部通过。整关详设用户说可以后，跑 `kit approve L<nn>/detail`（连同 D3 一起登记）。

## 常见坑

- 不看证据，按惯例脑补。照片和口述看得出来的，按看到的写；没有证据的，标“假设”并挂一个问题。
- 改设计前没查规划原文。规划里的决定是用户拍过板的。
- 一栋楼做完就停下等用户：用户被频繁打断，时间耗在来回上。
- 跳过结构事实清单直接画：结构理解错了，所有楼都要返工。
- 只写氛围、没写这是什么房间：生成线不知道房间做什么用。
- 把底稿当成给用户的材料交出去，问题只写“有没有某样东西”不写判断：用户要自己翻文件找你的推断，看两遍也不知道要回答什么。
