# G9 成品交付（每关一次）

**目的**：全关按规范和外观规则铺开，完整编译，硬标准全过才交。负责人只看本关第一次出现的类型和地标。

## 读

G3–G7 的产物；美术规范、G5 的外观规则 `work/style.json`；gaps.json 和问题清单里交给本线的条目。

## 做

1. **按规范和外观规则铺开**：构件记录里每一行按它的规则取材质或模型；按 key 的规则只管那一个，不推广。
2. 测试视点全部从数据推（起点、每个事件、每段路线、必达点、地标、终点）。
3. 完整编译：vbsp → 完整 vvis → vrad → 打包。整关不用 vrad -final；编译放后台，等的时候做别的。
4. 报告：预算、可见性、光照补丁、缺资源、成品检查、耗时。REPORT.md 由脚本生成；人工核对的结果在 `work/L<nn>/manual-checks.md`，REPORT 引用它。
5. **人做的产物哪些作废**（脚本）：和上次交付的构件记录 `work/L<nn>/delivered/parts.json` 按 key 比，几何或挡路物件变了就标“导航要重做”；按改动的设计元素 key 列出受影响的试走项。写进 `work/L<nn>/invalidated.json`，交给 G10。交付时把这次的 parts.json 复制到 delivered/。脚本做出来之前，由本步 agent 按 key 对比两份 parts.json，外包盒或挡路属性变了的行列出来；有一行就标“导航要重做”。
6. G4 之后新发现的影响玩法的问题都已写进 gaps.json，在这次拍板点一次交出；做不出的玩法实体按 [G4](G4-runtime.md) 第 8 条登记，不替代。更新生成线日志和 PROJECT.md 本线那一行；日志和拍板消息按实际编译出来的东西写（G4 第 9 条），还没解决的缺口在消息里逐条列明。
7. **交拍板前自查**：先跑完硬标准，再看俯视核对图；模型预览图逐张和参照照片比三项：正面朝向、长宽高比例、主色，哪一项不同就改，改不了的列进拍板消息的“只是告诉你的”。不把脚本能拦的问题留给负责人。
8. **交负责人拍板**：消息里列出要看的视点，由脚本筛 refs.json 里 types 的 approved 为空的类型和地标（之前的关已认可过的不再看），另加每个可进入结构体里路线经过的主要房间各一个视点（室内各不相同，不按类型省略）；G6 室内盲审改两次仍对不上的空间单列。消息里写明：脚本和室内盲审全过，只说明每个房间按意图做了、认得出，好不好看要负责人看；每个视点写看哪几项：光照、布景密度、模型精细程度、旧化程度。负责人认可的类型在 approved 写日期和关号。负责人的意见写回美术规范（变成数字或档位），再按“只改受影响的部分”改。意见里暴露出检查缺口的（脚本本该拦住却没拦），补检查脚本，在本次消息“只是告诉你的”里写明缺口在哪一步。

## 拍板登记

负责人说可以后，在 `design/REVIEW-LOG.md` 末尾追加一行固定格式：`- [拍板] <单元> <日期> sha:<指纹>：<原话摘要>`。单元写 G0、L<nn>/G4、L<nn>/G9、L<nn>/G10；指纹取这次拍板对象内容的 sha256 前 16 位：G0 取 standards/art.md，G4 取 work/L<nn>/gaps.json，G9 取 work/L<nn>/delivered/parts.json，G10 取 work/L<nn>/human-todo.json。生成线日志引用这一行；stamps 读最后一条同名的行，指纹对不上就当作拍板后又改过。`kit approve` 支持 G 单元之后，改为跑 `kit approve`。

## 完成

**硬标准全过**（脚本，一条命令在最终编译上全部重跑，任何一条不过不交）：

1. 构件记录里“白盒、凑合”为 0，包括 made_by 为 shell 和 generator 的行（工具材质用途表里的工具材质不算白盒；不留“看不见所以保留”的口子；只有设计数据标为白盒关的跳过），按面数统计的检查同时跑、两边对账；构件记录里没有“匹配失败”。
2. 工具材质只用在美术规范工具材质用途表列出的用途。
3. 模型：编译后外包盒和部件表一致；三角面数在所在精细档位范围内；摆放核对 0 条错。
4. 贴图：VTF 7.4、尺寸 2 的幂、文字不镜像（算上缩放的正负号）、拉伸不超阈值。
5. 依据：每个构件、布景组都有参照编号；第 1、2 档叙事痕迹都引用了设计数据；每项资源在 work/licenses.json 写明出处和许可。
6. 环境：布光规则、灯具和光源对应 0 条错；每种空间类型都有音景；vrad 补丁 ≤ vrad_patch_max。
7. 几何：无漏点；brushside、brush 不超 map_budget_ratio.goal 乘各自上限；坐标在 ±(16384 − map_margin_u) 以内；vis_ratio 低于 vis_ratio_max；覆盖检查通过。
8. 运行层：接线检查（目标、输入输出名）和事件对账通过；用到的实体类型都有原版用例或写了理由。
9. 玩法实体真实存在：设计里每个玩法实体（载具、电梯、事件门、安全屋门、按钮，开放区的 event_door，结构体里 state 为 event_open 的门），在编译后的地图里都有对应类型的实体：会动的是会动的实体类型（func_tracktrain、func_movelinear、prop_door_rotating 等），玩家要站、要挡的有碰撞。判定：按 parts.json 的 key 找到实体，核对类名在这种物件的允许类名里（允许类名表写在生成器里，和 [G1](G1-intake.md) 的对表同一份）；prop_static、不带碰撞的 prop_dynamic、只有 logic_relay 或 logic_timer 的一律不算。
10. 载具沿设计路线走：载具的 path_track 链按顺序经过设计路线的每个点（每点水平偏差不超过相邻 path_track 的间距），停车点和设计的停车点一一对应；把车体外包盒沿整条路径扫一遍，扫出的体积不与任何结构体的 brush、封路、围挡相交（地面和路面除外）。
11. 地面模型贴地：落在地面或台面上的模型（道具、构件、布景），编译后外包盒最低点和它脚下的地面、台面顶面高差不超过 ground_snap_tol_u。判定：从模型中心向下找最近的 brush 顶面或位移面，比较两个高度；挂在墙上、吊在顶上、设计写明悬空的不查。
12. 门和门扇：每扇做成门扇的门，门洞净宽和门扇总宽差不超过 door_leaf_fit_tol_u，净宽装不下一扇时用两扇（单扇、双扇按门扇模型的宽度判，不按名字）；门扇绕铰链从关到开的扫掠范围不与门框以外的 brush 和挡路构件相交。
13. 模型不穿建筑：模型外包盒（按转角算）伸进建筑 brush 的深度不超过 model_brush_intersect_max_u；贴墙摆的布景（摆放记录 placements.json 里标了贴墙的）只查有没有伸出墙的另一面。
14. 室内：每个建出来的空间都有室内意图对应的布景组（`has` 每项有组或写了不做的理由）、房间布置图和室内盲审记录；盲审全部对得上，改两次仍对不上的已在拍板消息里单列。

9–14 由各项目的生成器实现，读编译用的 VMF、模型外包盒和 spec，不需要启动游戏。容差是生成线新增的待决定项（见 [G0](G0-art-standard.md) 第 7 条），正文不写死数值。

负责人看完列出的视点、拍板，并已写拍板登记行。

## 常见坑

- 时间大量花在等编译和排查编译问题上：编译放后台，先用快速档验证。
- 把“脚本全过”写成视觉完成：硬标准只说明做到了、没做错，房间好不好看要负责人看。
- 白模只算了开发材质，灰盒时代凑合用的原版材质漏查。
- “负责人看好不好看”没写看哪里、看什么：要么整关逛一遍，要么漏看。
- 只查材质、跳过工具材质和模型摆放：报“0 面通过”，负责人一看全是错的。
- 检查只看平面（XY 朝向、重叠），不看高度和碰撞：箱子嵌进地里、车开进楼里、门扇比门洞窄一半，脚本照样全过。
- 工具材质用途写了两份：G9 的检查和 G3、G5 自己的做法冲突。
- 交接文件放在不提交的 build/ 下：清一次目录，人工核对结果和拍板依据全丢。
