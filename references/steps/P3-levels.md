# P3 切关与关卡设计

**目的**：定每关从哪到哪、玩什么、节奏怎样。一关一拍板。开头先把坐标和地基定下来，整个项目只做一次。

动手前读 [rules.md](../rules.md)。

## 先做（整个项目一次，只过脚本，不交用户拍板）

坐标必须在画任何路线之前定死；做到一半再定，所有尺度和时长都得重算。

1. **坐标**：选原点，写进 `campaign.json` 的 `geo.origin`（纬度、经度）。项目坐标用米，x 向东，y 向北。原点只影响坐标数字，取范围中部附近即可。
2. **防镜像**：在 `geo.landmarks` 登记 2–3 个影像上颜色明确、位置不对称的地物，每个写 `name`、项目坐标 `at` 和 `expect`（`green`、`water`、`bright` 或 `dark`）。跑 `kit geo check-mirror`：每个地标所在的点必须是预期颜色，南北镜像和东西镜像的位置都不能是这个颜色。
3. **地基数值**：在待决定列表里填 `step: "P3"` 的项（边距、路线留宽、面数预算目标和估算系数、压缩检查阈值）。这些是技术值和检查阈值，由你填一个默认值、写 `why`、标“暂定”，不问用户；用户看不到关卡之前无从判断。引擎事实已经预填（[engine-facts.md](../engine-facts.md)）。

真实度为“虚构”时没有真实坐标：只定地基数值，跳过第 1、2 项。`kit geo check-mirror` 通过、待决定列表里 P3 的项都有值，再开始切关。

## 做（每关一次）

1. **切关**：按“这里有没有玩法撑得住”选区域，不按名气。相邻两关共用一个安全屋（`design/plan/rooms.json`，坐标完全一致）。关与关之间要有对比：室内和室外、高压和低压、白天和夜晚。每关的时间和天气按需要定，写成字段。
2. **每关一个源文件** `design/plan/levels/L<n>.json`（字段见 [format/plan.md](../format/plan.md)）：路线途经点和每段的模式、段落、玩法、事件、资源、路障、刷怪口、守点。
3. **每个玩法写原版依据**：用哪个实体、哪张原版地图有先例。用 `kit game find <类名>` 查先例和接线方式，用 `kit game classes` 核对实体名。
4. **时长**：纯跑时间 × 2–3，再加守点等待，结果要落在 `campaign.json` 的范围内。`kit plan build` 会算出来。
5. **标出压缩候选，不做压缩决定**：符合下面任一条的路段，在源文件里标 `compress: true`，并写 `compress_why`：
   - 整关超出地图预算（`kit plan build` 报“超出”）；
   - 这一段长、没有玩法，是空跑（写长度和纯跑秒数）；
   - 这一段拖慢节奏，整关估时超出 `campaign.json` 的范围。

   压不压、压多少到 D1 才定：那时空间已经分级，能出压缩前后对照图给用户看。现在让用户定，只能凭空猜。
6. `DESIGN.md` 只写数据装不下的内容：职责、核心问题、段落叙述、背景（和玩法分开写）、技术风险、验收标准。

## 命令

`kit plan build` 寻路并合成 `levels.json`，`kit plan verify --no-render` 核验。`kit plan render` 出视图给用户看。

## 子 agent

**轻量档**，按玩法派：去原版地图里找先例，交回实体名、接线方式、出处。实体名必须能用 `kit game classes` 查到。

## 完成

`kit plan verify` 通过。一关交用户拍板一次（附这一关的规划视图；压缩候选列出来供参考，不要求用户现在决定），拍板后跑 `kit approve P3/L<n>`。

## 常见坑

- 一次出五关，大面积返工。
- 关卡内容写死在脚本里，换个项目就得重写。
- 文档和数据各写一份，最后对不上。
- 坐标换算链路里翻转了两次，整张图镜像，到评审时才发现。
