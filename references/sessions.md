# 会话、接力与返工

开会话、换会话、处理别的线交来的问题之前读这一页。平时不读。

## 三条原则

1. **会话只是干活的载体，权限来自文件归属和拍板。**每个文件只有一条线负责（见下面的归属表）。设计文件改了，拍板记录的指纹会让它变成“拍板后已修改”，谁改都绕不过用户。
2. **会话之间不发消息，只靠文件交接。**交接写进本线日志和问题清单，下一个会话开工读文件。会话结束、上下文压缩都不丢东西。
3. **会话只在段表列出的接力点换。**段内的其他停顿点（D1 有压缩候选时、D4 彩蛋）照常停下讨论，不换会话。一段没做完但上下文已经压缩过一次的，做完手上这一步就写交接、提前接力。

## 有哪些会话

- **总控**：同一时间只有一个，上下文满了换新的接班。做 P0–P4 和 D0；之后待命：开第一批设计①，处理没有线认领的问题（规划、待决定列表、跨关），把 Kit 的问题成批告诉用户，回答用户“现在整体怎样”。不做任何 D、G 步骤的活，不读其他会话的对话记录。
- **每关的段会话**：设计线三段、生成线三段，每段一个会话，两个接力点之间。
- **修订会话**（按需）：设计线结束后，别人交回这一关设计的问题时开。
- **子 agent**：在会话内部派，只交回给派它的会话，见 [subagents.md](subagents.md)。

同时开发的关不超过 `max_parallel_lines`（P0 问用户）。一关从设计① 开工到 G9 交付占一个名额；修订会话和等人工的生成③ 不占。修订会话同一关同时只有一个。

## 段表

| 段 | 做哪些步骤 | 结束时的接力点 |
|---|---|---|
| 设计① | D1；D2 先查结构事实 | 结构事实清单：用户答完、按 D2 记下回答（sources/oral/、FACTS.md 写确认日期），kit status 显示“已确认”，再接力 |
| 设计② | D2 画结构体、D3 画开放区，核验全过 | 整关详设 |
| 设计③ | D4 彩蛋（停一次）；D5；D6；D7，开本关生成① | 整关拍板 |
| 生成① | G0（只在第一关）；G1–G4 | G4 之后的停顿：只交问题 |
| 生成② | G5–G7；完整编译；G9 | G9 成品交付 |
| 生成③ | G10 | 人工任务清单全部有结果 |
| 修订 | 改交回的设计问题；核验；重新合成 spec；更新交接 | 条目都改成已修复或已驳回 |

## 谁开谁

- 总控开第一批设计①。每段在自己的接力点、用户说可以后，开下一段，然后结束。
- 设计③ 开本关生成①。
- 生成② 在 G9 拍板后开本关生成③；这一关让出名额，再开还没开工、关号最小的那一关的设计①。
- 发现问题的会话在自己的停顿点、用户同意修订后开修订会话。这一关已有修订会话在跑时不另开，在条目里标“待开修订”，由那个修订会话结束前接着改。
- 等修订的会话不新开、不结束。修订会话结束时，在交拍板消息的“只是告诉你的”里写一句“L<n> 的某某会话在等这条，回到那个会话说继续即可”。
- 自动开会话要用户在 P0 授权（`agents.auto_handoff`）。没授权时，到接力点把三句开场白写好，交用户去开。授权后，按这一节在固定接力点开会话不算“跨关推进”。
- 开会话时设标题“<项目简称> L<nn> <段>”（例：“ABC L02 生成①”），总控是“<项目简称> 总控”；项目简称取 kit.local.json 的 `project_short`。没授权自动开会话的，开场白第一行写这个标题。
- 每段结束时，给用户的消息里写明开了哪个会话、结束了哪个会话。

## 交接

**结束的会话写**：本线日志 `logs/L<nn>-design.md` 或 `logs/L<nn>-build.md` 追加一节：这段做完了什么；用户这次的决定（原话写进 design/REVIEW-LOG.md，日志只写“见 REVIEW-LOG <日期>”）；留下的“假设”和它们影响哪些产物；本段新登记的问题编号；下一段从哪一步开始。PROJECT.md 只改主线分工表里本线那一行（现在第几段、哪个会话、状态），不追加长段落。提交只 add 自己改的文件，不用 `git add -A`。

**新开的会话读**，只读这些：SKILL.md、PROJECT.md、`kit status`；本线日志最后一节；交给本线、还没关闭的问题（`kit status` 还不列问题时，用几行脚本按 to 和 status 筛，不读整份清单）；当前步骤页。`kit status` 还不认识 G 步骤时，生成线的当前步骤以本线日志最后一节为准。

## 问题登记

- **设计交出去的**：用 Kit 的 `followups.json`（kit spec 生成）。生成线关掉交给它的项，写 `design/detail/L<nn>/followups.closed.json`。交给用户的项不能这样关。
- **生成线交回设计的**：写 `work/L<nn>/gaps.json`，字段见 [D7](steps/D7-handoff.md)，另加 status。
- **其余跨线的**（交给规划、跨关、没有线认领的）：写项目根的 `issues.json`，字段同 gaps.json。线内的问题和偏差照现有做法写在设计文件里，不重复登记。
- **Kit 的问题**不登记，在停顿点告诉用户（硬规则）。改不改 Kit 由用户在流程外决定。

条目状态：待处理 → 已答复 → 已修复 / 已驳回（二选一）→ 已关闭。只有接收方能改成已修复或已驳回；只有发现方能改成已关闭。“发现方”指一条线：由这条线当时在跑的会话关闭，整条线都结束了由总控关闭。

**重开**：发现方把“已修复”或“已驳回”的条目退回“待处理”，或者对同一个设计元素（elements.json 的 key）再登记一条。同一个 key（没有 key 的按条目 id）第 3 次重开时，重开它的会话停下交用户查根子。

**挡路才停**：不挡后面全部工作的，带着“假设”继续做，在条目里写清假设影响哪些产物；改完只重做这些。影响 G3 几何或导航的假设当挡路问题；只影响 G4–G7 的照做并登记。问题攒到本段的停顿点一起交。

## 修订会话

开工读：SKILL.md、PROJECT.md、`kit status`；开场白给的条目编号；`kit status` 指向的步骤页；要改的那几个文件。只改问题清单里登记过、用户在停顿点同意修订的条目。按 D2、D3 的规则改、核验，重新合成 spec，更新交接。用户已在生成线的停顿点答复过这条取舍、修订只改了这一处的，直接 `kit approve`，原话写进 REVIEW-LOG.md，在下一次拍板点的“只是告诉你的”里带过；超出原话范围才重新交拍板。结束前查这一关有没有标“待开修订”的条目，有就接着改；结束时不开后继。

## 返工

- **机器部分**（生成、核验、快速编译）整体重跑；**AI 和人的工作**只改受影响的那几处：改哪里只碰那个文件的那几处；AI 的产物（参照板、布景、外观规则）只改引用了改动处的条目；拍板只交改动的那几条；人的产物只重做受影响的部分（试走只重走涉及的项；导航网格受工具限制整关重生成）。
- 规划改了：总控改完、重新拍板后跑 `kit spec`；核验没过、或引用了改动处的，登记给这一关的设计；设计线已结束的走修订会话。
- 盲审改了路线或玩法的，再审只给改动处；第二次盲审仍有设计问题的，不再派盲审，直接交用户。
- 生成器改了：在 `build/_regress/` 对已完成的关重新生成并比对，不写 `build/L<nn>/`。完全一致就提交；退步就修到一致；变好了而且那一关已交付的，登记给总控，由用户决定要不要重新交付。没有生成线在跑时，生成器的问题交给下一条开工的生成线。

## 依赖：改了什么，哪些要复查

| 改了什么 | 要复查的 | 人做的产物作废 |
|---|---|---|
| 结构体或开放区的几何 | 设计：本文件核验 → D5 → D6 再拍板。生成：G3 → 受影响的段的 G5–G7 → G9 | 导航；涉及这段的试走项 |
| 物件、事件、物资 | 设计：核验 → D5 → D6。生成：G4 → 有外观的 G6 → G9 | 涉及的事件试走项；物件挡路时导航 |
| 分级、地标 | 设计：D1 估算。生成：G2 → G5 → G9 | — |
| layout（原点、朝向） | 设计：D5。生成：G3 起全部 | 导航、试走全部 |
| 规划 | 规划视图 → 引用它的结构体和开放区 | — |
| 待决定列表 | 读过这一项的核验报告（Kit 自动判）；生成线的 stamps 同样记下读过的项 | 视值而定 |
| 美术规范 | G2 → G5–G7 → G9；已完成的关回归 | — |
| 生成器 | 改到的那层 → G9；已完成的关回归 | 比对有变化时导航、试走 |

生成线的过期判断：每个 G 步骤跑完写 `build/L<nn>/stamps/G<k>.json`，记下它读过的输入的指纹（spec 里用到的部分、读过的待决定项和它们的指纹、生成器版本、美术规范、参照板、拍板登记行）。开工和每一步之前比对，就知道从哪一步过期；记下的产物在 build/ 里不存在的也算过期。

## 文件归属

| 文件 | 归谁 | 别人发现问题 |
|---|---|---|
| design/plan/ | 总控 | 登记交给规划；偏差先写设计文件的 plan_deviations，用户拍板后再改 |
| design/detail/L<nn>/（followups.closed.json 除外） | 这一关的设计线；设计线结束后只有修订会话能改 | 登记交回设计 |
| design/detail/L<nn>/followups.closed.json | 这一关的生成线 | — |
| kit spec 生成的 spec.json、spec.check.json、elements.json、followups.json、handoff.json | 谁都可以跑 kit spec 重新生成，不手改 | — |
| standards/decisions.json | 值为空的项由 step 所在步骤的执行者首次填写；填了以后的修改（含暂定改已定）归总控；生成线新增的项归新增它的那条生成线 | 登记交给总控 |
| standards/art.md、work/ 下除 L<nn>/ 以外的文件、生成器 | 各关的生成线共用，按下面的共用文件规则改 | 登记给正在跑的任一条生成线；都没在跑时，交给下一条开工的 |
| work/L<nn>/、build/L<nn>/ | 这一关的生成线 | — |
| sources/ | 谁都能追加（kit sources add 分配编号），不改别人的条目 | 勘误写 errata |
| design/REVIEW-LOG.md | 谁都能追加，只追加 | — |
| design/approvals.json | 只由 kit approve 写 | — |
| PROJECT.md | 总控；每条线只改主线分工表里自己那一行 | — |
| HUMAN.md | 总控（只写通用方法） | 登记交给总控 |
| issues.json | 谁都能新增；状态按上面的规则改 | — |
| kit.local.json | 总控（P0 写） | — |
| logs/L<nn>-*.md | 这条线 | — |

所有会话共用一个工作区和暂存区。提交写明路径（`git commit -m … -- <路径>`），不用 `git add -A`。共用文件（decisions.json、资料库、生成器、美术规范、work/ 下除 L<nn>/ 以外的文件）改之前先看 `git status` 有没有别人未提交的改动，有就等它提交；改完立刻提交。只有本关用到的配置放 work/L<nn>/。别的关改了共用文件，靠 stamps 发现，按依赖表重跑。
